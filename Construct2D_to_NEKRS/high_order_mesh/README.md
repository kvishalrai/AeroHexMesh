# Step 4: apply the wall correction, and run NekRS

This is the last step of the pipeline described in
[`../linear_mesh/README.md`](../linear_mesh/README.md#the-algorithm).
Everything up to here has been *preparing* files; this is where they
finally get combined and a real simulation runs.

## What this step actually does

Recap of where the two input files came from:

- **The 3D mesh** (step 3) has the right shape and the right boundary
  tags, but its wall is still the jagged, faceted approximation — the
  smoothing correction from step 2 hasn't touched it yet.
- **The correction file** (step 2) only describes the fix for the flat 2D
  cross-section, not the real 3D mesh.

This directory (`example_nekrs/`) is a NekRS case whose setup code
(`usrdat2`, calling a routine named `get_smooth_data`) reads that 2D
correction file and copies it onto *every* spanwise slice of the real 3D
mesh — since the 3D mesh is just the 2D cross-section repeated along the
span, the same 2D fix is valid at every repeat. No new curve-fitting
happens here; this step is pure copy-and-apply. Once that's done, NekRS
runs the actual airflow simulation on the now-smooth mesh.

## Where the input files come from

Only the hand-written case files are tracked in git here — the mesh and
correction data are generated by the earlier steps and copied in (see
[`../linear_mesh/README.md`](../linear_mesh/README.md#running-it-end-to-end)):

| File (gitignored, not tracked) | Produced by |
|---|---|
| `naca.re2` (the 3D mesh) | step 3, `linear_mesh/arglist.sh` — written directly here via its `output_re2` argument |
| `geom_3x3_naca_gen_spline_info.dat` (the correction) | step 2, `linear_mesh/smooth_2D/`'s `nek5000` run — copy in by hand |

Everything else here (`naca.usr`, `naca.par`, `naca.udf`, `naca.oudf`,
`ci.inc`, `ci.oudf`, `intercept.oudf`, `my_drag.oudf`, `naca.nek5000`,
`nekrs.upd`, `airfoil0.sh`) is hand-written case configuration, and *is*
tracked in git normally.

Don't track anything NekRS itself writes when you run it either
(`.cache/`, `base.fld`, `naca0.f*` restart/output fields, `newrea.out`,
`cmake.log`, SLURM's `out.o`/`error.e`) — those are gitignored; just
rerun the case to regenerate them.

## Before running: two things `compute_case_params.py` doesn't touch

Step 3's `arglist.sh` (via `compute_case_params.py`) already fills in
`naca.usr`'s `NUMBER_ELEMENTS_X/Y/Z` and `naca.par`'s matching
`[CASEDATA] number_elements_x/y/z` automatically, from the mesh itself —
you shouldn't need to touch those by hand. Two other settings are real
physics choices, not mesh-derived, so they're **not** automated and are
easy to leave inconsistent if you change one but not the other:

1. `naca.par`'s `[VELOCITY] viscosity` (given as `-Re`, e.g. `-5.0e4` for
   Re = 50,000) and `[CASEDATA] p_aoa`/`p_u0` (angle of attack and inflow
   speed) — set these to whatever case you actually want to run.
2. `naca.oudf`'s `codedFixedValueVelocity` function, which sets the
   inflow direction on the GPU. It's a **hardcoded** angle, not
   automatically linked to `naca.par`'s `p_aoa` — a NekRS quirk (values
   set in `UDF_LoadKernels` aren't visible inside this particular kind of
   GPU kernel), not a bug to try to fix here. **If you change the angle
   of attack, update it in both places by hand**, or the inflow direction
   used by the actual physics will silently disagree with what you think
   you set.

## Running it

```bash
sbatch airfoil0.sh
```

from this folder. Open the script first — it's specific to this cluster
(BSC MareNostrum 5) and currently assumes a working NekRS install already
exists at a fixed path; see its own comments.

## How to tell if it worked

Log lines to look for, roughly in the order they appear:

1. **`building nekInterface for lx1=..., lelt=N and lelg=N`** — `N` should
   match the element count `arglist.sh` reported when it wrote the 3D
   mesh in step 3 ("... elements written"). If it doesn't, the wrong mesh
   file ended up here.
2. **`loading nek ... done`** — means `usrdat2`/`get_smooth_data` (the
   step that applies the wall correction) ran without crashing.
3. Once the simulation is actually stepping forward in time, watch the
   `t-cd-cl` line (drag and lift coefficients) and the velocity/pressure
   min/max NekRS prints every step. `Cd`/`Cl` should be small, physically
   reasonable numbers (order 1, or less), not astronomically large. The
   time step `dt` should stay roughly steady. If `dt` keeps shrinking
   while velocity/pressure values keep growing, that's the simulation
   *diverging* — a sign of a physics/numerics problem (e.g. too
   aggressive a time step for the mesh resolution), not a mesh or
   boundary-condition problem, since those are covered by points 1–2
   above.
